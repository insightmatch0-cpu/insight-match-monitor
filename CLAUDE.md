# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the complete context for the InsightMatch football monitoring & prediction system. Any AI agent working in this repo must read this first and follow it exactly.

## Who the user is

Nayef — the owner and sole operator. **No coding experience.** Always explain in plain language, provide step-by-step instructions for anything manual, and never assume he can debug code himself. He works mostly from an iPhone, sometimes a Mac. Communication may be voice-transcribed (tolerate imprecise wording; confirm intent when ambiguous).

## What this system is

A fully automated football match monitoring, alerting, and self-learning prediction system running entirely on free/low-cost infrastructure:

- **GitHub Actions** (public repo = unlimited minutes) — all automation. Python 3.12, sole dependency: `requests` (installed per-run in workflows; there is no requirements.txt)
- **API-Football** (api-sports.io, **Pro plan: 7,500 requests/day**) — match data. Key in GitHub Secret `API_FOOTBALL_KEY`
- **Anthropic Claude API** (model `claude-haiku-4-5-20251001`, set as `CLAUDE_MODEL` in each script) — all analysis & predictions. Key in Secret `ANTHROPIC_API_KEY`
- **Telegram bot** — alert delivery. `TELEGRAM_TOKEN` + `TELEGRAM_CHAT_ID` in Secrets
- **GitHub Pages dashboard** — https://insightmatch0-cpu.github.io/insight-match-monitor/

## The self-learning loop (core logic — preserve it)

1. Every prediction is stored with pick (`home|draw|away`) + confidence (prompt asks for 40–80; parser clamps to 30–85).
2. Next morning, `predict.py` fetches real results and grades each prediction — **on the 90-minute score** (`score.fulltime`, falling back to `goals`): a knockout match decided in extra time/penalties still grades as a draw if level after 90, matching the universal 1X2 convention (and the odds fed to V2).
3. Accuracy is computed: overall, last 30 days, top vs other leagues, daily series (last 30 days), and **by confidence bucket** (70+, 60-69, 50-59, <50).
4. That track record is injected into every new Claude prediction prompt with the instruction: *if your real accuracy is below your stated confidence, lower your confidence — and vice versa.* This calibration IS the learning mechanism. Never remove it.

## Engine 2 (V2)

The second-generation prediction engine (`predict_v2.py`), built to run side-by-side with Engine 1 for a fair, direct comparison. Design decisions — preserve them:

- **Same fixtures as V1**: identical next-24h selection, exclusion lists, `TOP_LEAGUE_IDS`, and `MAX_PREDICTIONS_24H=150` (raised from 60 on 2026-07-18 so later-kickoff evening matches are also predicted — otherwise they showed live on the dashboard with no engine 'protection' chip; must stay identical in both engines, guarded by `tests/test_exclusions.py`), so accuracy numbers are comparable engine-to-engine.
- **Model**: `claude-fable-5` (V1 stays on Haiku).
- **Enriched context, top leagues only by default** (`ENRICH_TOP_ONLY=True`, cost control 2026-07-17): the heavy enriched prompt (and Fable's cost on it) is spent on top-league fixtures; every other fixture is still predicted and graded, just with the lean prompt — so coverage, grading, calibration, and lessons are unchanged, only the token bill drops. Set `ENRICH_TOP_ONLY=False` to instantly restore rich context for every fixture. When a fixture is enriched, extra API-Football data is fetched before predicting — standings of both teams (1 call per league, cached per run), head-to-head last 5, each team's last 5 results, injuries, **bookmaker odds** (first bookmaker's Match Winner odds, converted to implied probabilities with the overround removed — the prompt instructs Claude to treat the market as a strong reference but diverge with a stated reason), and **API-Football's own statistical prediction** (percentages + advice). `MAX_ENRICHED_FIXTURES=60` caps how many fixtures may be enriched, and `ENRICH_CALL_BUDGET=750` caps the extra calls/run as a safety net; enrichment failures degrade gracefully to a basic prediction (never kill the run).
- **Probability output**: each prediction returns `prob_home`/`prob_draw`/`prob_away` as integers summing to 100 (parser normalizes if they don't). `pick` = highest probability; `confidence` = that probability clamped 30–85. Probabilities are stored in pending AND resolved entries.
- **Cup/knockout guardrail (`CUP_GUARDRAIL`, owner's priority 2026-07-18)**: the owner watches the **70%+ confidence bucket** closely — it must stay near-perfect. Its single miss was a domestic-cup upset (Kerry 2-2 Shelbourne, FAI Cup, engine gave the away favourite 72%). Fix: `apply_cup_guardrail()` runs after the model on cup/knockout fixtures (`is_cup_fixture()` flags them by league-name/round keywords — cups + UEFA qualifiers) and (a) raises the draw probability to a floor `CUP_MIN_DRAW=25` — cup upsets are common, and (b) caps confidence at `CUP_CONF_CAP=65` so cup guesses can never enter the 70%+ high-conviction tier. It **never changes which side is picked** (the draw floor never exceeds the favourite) and **does not touch learning** — calibration + lessons still grade against the real result. The engine's own lessons loop already learned this pattern ("beware >70% confidence in cup matches"); this converts that soft lesson into a hard guardrail for the high-stakes tier. Instant revert: `CUP_GUARDRAIL=False`.
- **Batching**: enriched fixtures in batches of `ENRICHED_BATCH_SIZE=4` (context is bulky), basic fixtures in batches of `BASIC_BATCH_SIZE=12` like V1. Strict JSON output, tolerant parser — same rule 6.
- **Own memory**: `predictions_v2.json` (`pending`/`resolved`/`meta.stats`), fully separate from V1, with the exact same grading, resolution, and calibration-stats logic — the calibration record is injected into every V2 prompt just like V1.
- **Lessons loop (Phase 3 — LIVE)**: every morning, after grading, `generate_lessons()` sends up to `MAX_MISTAKES_PER_RUN=30` (i.e. effectively ALL) of yesterday's WRONG predictions to Claude in one call, which extracts one short, generalizable Arabic lesson per mistake (a pattern to watch for, not a description of the game). Lessons are stored in `lessons_v2.json` as `{"date","match","text"}` (capped at `MAX_LESSONS_STORED=100`); the most recent `MAX_LESSONS_IN_PROMPT=15` are injected into every prediction prompt under "دروس من أخطائك السابقة". **Consolidation**: when stored lessons exceed `CONSOLIDATE_THRESHOLD=60`, one Claude call merges similar lessons into ≤`CONSOLIDATE_TARGET=30` stronger general principles (entries labeled "خلاصة مُجمّعة"); on any parse failure the original lessons are kept untouched. The newest 10 lessons also appear on the dashboard (V2 tab) and the digest notes how many new lessons were learned. Note: calibration (the accuracy record in every prompt) already learns from ALL graded matches — the lessons loop is the qualitative layer on top.
- **Telegram digest** is labeled "🤖 المحرك 2" so V1 and V2 messages are distinguishable; it shows the three probabilities per match AND, for each match, Engine 1's pick next to Engine 2's pick (read from `predictions.json` pending — V2 runs 15 min after V1 so V1's picks already exist). The side-by-side comparison lives in the V2 digest only; V1's digest is unchanged.
- **Live layer (in `monitor.py`)**: top-league live matches are analyzed by `claude-fable-5` with **extended thinking** (`LIVE_THINKING_BUDGET=2048` tokens of deep reasoning before answering) fed with real live statistics + events + **lineups/formations** (3 API calls per match) and an all-scenarios prompt. Capped at 12 matches per run. **Scenario menu (`SCENARIO_MENU_V2`, owner's market-style list 2026-07-15, shared by the event analysis AND the pulse)**: next goal + likely scorer/assister by name, both-teams-to-score, total-goals trajectory (open/closed game), corner waves + which team wins most, set pieces (dangerous free kicks, long throw-ins near the box, repeated goal kicks/clearances as pressure signals), cards (named player likely to be booked, game-changing red, both teams carded), goalkeeper under siege (repeated saves), repeated offsides killing attacks, and endgame shape (winning margin, which half has more goals, HT/FT swing, leader closing the game). The live stats fed in include shots on/off/blocked/inside/outside box, offsides, saves, fouls (`KEY_LIVE_STATS`).
- **Logo self-repair**: both engines backfill missing `home_logo`/`away_logo`/`league_logo` on pending entries from the daily fixtures fetch, and fill them from the results fetch at resolve time — zero extra API calls.
- **Budget**: 2 fixture-date calls + ≤3 resolve calls + enrichment (typically ~385 incl. odds + model predictions, hard-capped at 600) ≈ ~400/day on top of V1's 5.

## Analysis methodology (the user's expert framework — apply in all analysis)

**Pre-match factors:** league position; motivation (title race / qualification / relegation); first or second leg + first-leg result; home/away records; current streaks; head-to-head; key injuries & suspensions; goals scored/conceded (attack vs defense); form trajectory last 5–6 games; manager situation (new appointment bounce / under pressure); fixture congestion & rotation risk before bigger matches; derby/clásico factor (these defy logic).

**Live-match additions:** xG; shots on/off target; possession *tied to real danger* (possession alone deceives); key passes; dangerous attacks (note surges in final 10–15 min); corners; red cards (who, when, position); current minute; score-line behavior (is the leader defending or pushing); substitutions (extra striker vs closing the game).

**Output format for any prediction:** short focused analysis of relevant factors only → clear final verdict: winner or draw + confidence % → for live matches, likely next scenario. Occasionally remind (briefly, not every reply): predictions are analytical opinions, never guarantees.

## Hard rules (never violate)

1. **Coverage exclusions:** friendlies, African competitions (CAF/AFCON/keyword "africa"), all leagues from India, Pakistan, Bangladesh, **and — clean-data directive 2026-07-18 — women's leagues, youth/age-group leagues (U16–U23, Primavera, youth championships), and reserve/academy teams**: the owner wants the brain built ONLY on senior men's football ("no rubbish data"); this refines quality-rule 4b — "every available match" means every available *senior men's* match. Guarded by `tests/test_exclusions.py` (four-file sync + real league names both ways). The `EXCLUDED_COUNTRIES` / `EXCLUDED_LEAGUE_KEYWORDS` lists (and `TOP_LEAGUE_IDS`) are duplicated in `monitor.py`, `scan.py`, `predict.py`, and `predict_v2.py` — any change must be applied to all four in sync. **Owner's priority leagues (2026-07-17), all kept in `TOP_LEAGUE_IDS` so they get the premium treatment — deep analysis, alerts, digest priority — and (under `ENRICH_TOP_ONLY`) Engine 2's rich context:** English Premier League (39) + Championship (40), Italian Serie A (135), German Bundesliga (78), Spanish La Liga (140), French Ligue 1 (61), Saudi Pro League (307), Bahraini Premier League (417), Iraqi League (542). Everything else stays covered but lean/cheap.
2. **Language convention:** ALL Telegram and dashboard-facing output in Arabic — team/league/country names in standard sports-media Arabic — but numerals always Latin digits (0-9), never Arabic-Indic (٠-٩). Arabic names come from Claude calls and are cached (in `state.json` / `predictions.json`) to avoid repeat calls.
3. **Secrets discipline:** keys live ONLY in GitHub Secrets. Never in code, files, chats, screenshots, or logs. **Never print a key or embed it in an error message** (this caused a real leak once — see history). All scripts `.strip()` env values to survive pasted whitespace.
4. **Quality first, cost smart (user's overriding directive 2026-07-17): NEVER sacrifice prediction or learning quality to save money.** Quality is the top priority; cost is managed by spending *smart*, not by cutting corners. Concretely: (a) the owner's priority leagues always get the full premium treatment, no compromise ever; (b) every available match — even off-season/obscure ones — is still predicted and graded so the engine keeps learning now and is fully loaded by August; (c) the biggest quality risk of all is the engine going dark from an empty Anthropic balance (it happened 3× in July 2026), so protecting the credit balance IS protecting quality — that is why cheap matches get the lean prompt (the rich data mostly doesn't exist for them anyway) while calibration + lessons still learn from them. If ever forced to choose, keep the priority leagues at full quality and keep the engine alive over enriching throwaway fixtures. **Cost philosophy (2026-07-14): spend API-Football freely, spend Claude wisely.** API-Football Pro (7,500/day) is prepaid — more calls cost nothing, so never skimp on data that improves predictions. Current usage: monitor ≈144/day polling (every 10 min) + up to 36/run for Engine 2 live context (3 calls × ≤12 top-league matches on start/goal events), predict ≤5/day, predict_v2 ≈400/day (enrichment incl. odds + statistical predictions for all 60 fixtures, capped 600). Total worst case ≈1,150/day — still lots of headroom. The Anthropic API bills per call, however, so keep Claude calls batched and purposeful — that's the real cost driver, not API-Football.
5. **Empty data ≠ error:** no live matches can simply mean rest day / off-season. Interpret correctly and pivot to upcoming fixtures instead of reporting failure. (`scan.py` already sends a friendly "no live matches" message; `monitor.py` exits cleanly.)
6. Claude batch predictions must return **strict JSON** (no fences, no prose); parsers are tolerant (fence-stripping, bracket extraction) but don't rely on it. `scan.py` uses a numbered `N| ... | ...` line format instead — equally strict.
7. **Engine-2-only by default (user's explicit rule 2026-07-15):** every change, enhancement, or new capability goes to Engine 2 ONLY unless the user explicitly says to touch Engine 1. Engine 1 stays frozen as the comparison baseline.

## The Focus List (قائمة التركيز)

Telegram is a two-way control channel, not just alerts. `watchlist.py` runs at the start of every monitor cycle (every 10 min):

- It reads new Telegram messages via `getUpdates` (**only** from `TELEGRAM_CHAT_ID` — messages from any other chat are ignored entirely; the offset is stored in `watchlist.json`).
- The user texts match names in plain Arabic/English (voice-transcribed, typos tolerated); one Haiku call interprets intent (`set`/`add`/`remove`/`clear`) against the day's pending fixtures and updates `watchlist.json`. The bot replies with a confirmation showing both engines' predictions for the chosen matches.
- Texting "مسح"/"مسح حي" fires the Live Scan workflow directly (no Claude call). "امسح القائمة" clears the list.
- **Alert gating in `monitor.py`** (`should_alert()`, guarded by `tests/test_should_alert.py`): watchlist non-empty → live Telegram alerts (start/goal/FT + Engine 2 live analysis + pulse) for watchlist matches ONLY; **watchlist empty → NO live alerts at all (total silence — owner's request 2026-07-26; the earlier "empty → top leagues" fallback is removed, and the alert-everything mode was already gone).** This gates ONLY the live monitor alerts — the two morning prediction digests + the grading/scorecard messages are sent from `predict.py` / `predict_v2.py`, never pass through `should_alert()`, and therefore still arrive every day even when the Focus List is empty (owner keeps these; decided 2026-07-26). Claude live analyses are only spent on matches that will actually be alerted. Data collection, dashboard, and daily predictions still cover everything regardless of the list.
- Watchlist matches get **VIP live treatment**: they take priority for Engine 2 deep live analysis regardless of league.
- **Pre-match scenario report (تقرير ما قبل المباراة — owner's request 2026-07-15)**: for each watchlist match, ~45 min before kickoff (`PREMATCH_REPORT_MINUTES=45`, temporarily widenable via the `prematch_window` workflow_dispatch input → `PREMATCH_WINDOW` env), `prematch_reports()` in `monitor.py` sends one "📋 تقرير المحرك 2 — ما قبل المباراة" Telegram message: the V2 model (extended thinking) covers the full `SCENARIO_MENU_V2` pre-match — expected result + winning margin, BTTS + over/under 2.5, likely scorer by name, corners (who wins more + total estimate), cards incl. named candidates + red-card odds, set pieces, half patterns, key battle — each with an estimated probability. Context = both engines' picks + owner's pick + 4 API calls (lineups if announced, injuries, bookmaker 1X2, API-Football statistical prediction) + the latest 15 lessons from `lessons_v2.json`. Sent once per match (`prematch_sent` flag in watchlist.json, saved immediately); skipped if kickoff passed; Claude failure → retried next cycle. Runs at the very start of every monitor cycle. **Self-grading loop (owner's request 2026-07-15)**: each sent report is captured in `scenarios_v2.json` and graded next morning against the real final data — see that file's row in the repo table.
- **Shadow reports (تقارير الظل — owner's directive 2026-07-18; KEPT as a permanent feature, DAY-10 FINAL verdict 2026-07-28)**: every monitor cycle, `shadow_reports()` in `monitor.py` writes a full pre-match scenario report for up to `SHADOW_REPORTS_PER_DAY=6` priority-league fixtures that are NOT on the Focus List — `select_shadow_fixtures()` picks top-league matches inside the `PREMATCH_REPORT_MINUTES` window, nearest-kickoff first, skipping any already captured or on the watchlist — and stores each with a `shadow:True` flag in `scenarios_v2.json`, sending **no Telegram** (silent). Each is graded next morning exactly like a watchlist report and feeds `lessons_v2.json`, so the engine trains daily on senior-men's priority football even on days the owner sends nothing. Guarded by `tests/test_shadow_reports.py` (top-only, in-window, no-duplicate, daily-cap). **DAY-10 FINAL verdict (the owner delegated the keep/widen/narrow call to the agent): KEEP AS-IS at 6/day — NOT widened, NOT narrowed** (decided 2026-07-28; confirms the 2026-07-23 interim keep). Evidence from `origin/main` at day 10: **18 shadow reports graded** (Jul 21–23, cap respected exactly at 6/6/6) + 3 watchlist reports. Scorecard accuracy shadow **37% (51/138 bullets)** vs watchlist **50% (11/22)** — but heavily confounded and both samples tiny: the shadow set was half UEFA CL qualifiers (hard cup ties) plus MLS/Brazilian, the watchlist set was 3 cup reports. Lessons layer clearly USEFUL not noise: the report-grading loop produced fresh *generalizable* tactical heuristics (cards-when-trailing, possession≠corner-majority, keeper-absence→raise BTTS, class-gap→scoring-collapse) with consolidation active. No harm to the match engine: V2's `history.json` daily trend held and V2 beat V1 on 11/13 days; the **70%+ confidence bucket stayed 17/18 (94%) — cup guardrail intact, no new high-conviction misses**. Cost safe: the shadow cap was respected and the Jul 26–28 Anthropic outage was a billing/account mismatch (credit funded in the wrong org), NOT shadow over-consumption — since fixed (new key in the funded org + auto-reload). **Why not widen now:** (a) the binding constraint is grading throughput (`MAX_SCENARIO_GRADES_PER_RUN=6`) — raising capture alone would only grow an ungraded backlog; (b) days 8–10 produced **no new trial data** (deep off-season → scarce top-league fixtures + the balance outage), so the Day-10 sample is essentially the Jul 23 sample — too small/confounded to justify a widen; (c) widening grading raises Claude cost immediately after a balance crisis. **Re-evaluation trigger:** revisit widening (raise `SHADOW_REPORTS_PER_DAY` and/or extend beyond top leagues) after ~2 weeks of August season data, once the sample is larger and less cup-confounded and auto-reload has proven balance stability. **Why not narrow:** the mechanism demonstrably adds useful lessons at negligible, capped cost. The one real defect surfaced during the trial (grading starvation by fixture-id sort) is fixed (oldest-first, see the `scenarios_v2.json` row).
- **Engine 2 live pulse (نبض المحرك 2)**: for watchlist matches ONLY, every monitor cycle with no goal/start/FT event runs a pulse — `live_pulse()` in `monitor.py` fetches full live details (3 API calls) and asks `claude-fable-5` (extended thinking) whether a NEW significant scenario is forming vs its previous reading (the full `SCENARIO_MENU_V2`). Reply "لا جديد" → silence; otherwise a "👁 عين المحرك 2" alert is sent. The last reading is stored in `state.json` (`pulse` field; a goal's enriched analysis becomes the new baseline) so each pulse compares against the previous one — no repeated alerts for the same situation. Caps: `MAX_PULSE_PER_RUN=12` Claude calls/run, statuses `1H/2H/ET` only (no HT/penalties).
- **Fast watch (الرصد السريع — owner's request 2026-07-15: alerts within 1-2 minutes)**: after the normal pass, if any watchlist match is live (or kicks off within 12 min), `focus_fast_watch()` keeps the run alive up to `FOCUS_LOOP_BUDGET_SECONDS=6*60` — **bounded by `fast_watch_deadline()`, which anchors the deadline to the run's START (`RUN_START`) and hard-caps total monitor.py wall clock at `RUN_WALL_CLOCK_BUDGET_SECONDS=7*60`, so a run can never outlast its 10-minute slot no matter how long the normal pass took (jam fix 2026-08-06, see history)** — and re-checks ONLY the watchlist fixtures every `FOCUS_SWEEP_SECONDS=90` via one `fixtures?ids=` call. Goals/kickoff/FT are alerted immediately with full Engine 2 analysis; between events a pulse fires ONLY when the numbers actually moved — `live_signature()` (1 stats call) vs the stored `sig` baseline, thresholds in `SIG_THRESHOLDS` (+2 corners, +2 shots on goal, +3 total shots, any card, +2 saves). This keeps Claude cost tied to real developments while alert latency is ~90s. The 10-min runs hand over seamlessly (monitor.yml concurrency queues, never cancels); with no live watchlist match the loop exits instantly (zero cost on normal nights). API-Football cost during a focus evening: ~7 ids-calls + ~7 stats-calls per match per 10-min run — negligible on the Pro plan.
- Entries expire 2 days after their match date so the list never mutes future days.
- `watchlist.json` is bot-written and auto-committed by monitor.yml.
- **The owner's own predictions (سباق الدقة الثلاثي)**: after confirming a Focus List, the bot sends one message per match with **three inline buttons** (فوز المضيف / تعادل / فوز الضيف) — one tap records the pick (button callbacks arrive via `getUpdates` as `callback_query`, processed with NO Claude call; `answerCallbackQuery` is best-effort since polling latency usually exceeds its window). Typing the prediction as text still works ("الريال يفوز وتعادل فرنسا" → the Haiku interpreter returns `action:"predict"` with picks). Picks are stored in `predictions_user.json` (same pending/resolved/meta structure, fixed `confidence: 60`, entries copied from V2 pending for names/logos; picks for already-kicked-off matches are refused; re-predicting before kickoff overwrites). Every morning `predict_v2.py` resolves them with the same `resolve_pending` logic and the V2 digest shows the three-way race line: "🏆 سباق الدقة — أنت | المحرك 1 | المحرك 2". Auto-committed by monitor.yml and predict_v2.yml.
- **Instant end-of-day summary**: `monitor.py` records each Focus-List match's final score into `watchlist.json` (`matches[fid].result`) at its FT event; the moment ALL watchlist matches have results, it sends "🏁 انتهت كل مباريات قائمة التركيز" with per-match ✅/❌ for the owner and both engines plus a day tally — sent once per list (`results_sent` flag, reset whenever the list changes). This is informational only; official grading/lessons stay in the morning run. The unchanged morning digest still goes out as usual.

## Project history & lessons learned

- **The WK-League incident (2026-08-01) — the data-quality doctrine.** The clean-data filter was a keyword blocklist, and blocklists FAIL OPEN: 4 women's leagues whose names carry no keyword (WK-League, Kvindeliga, Damallsvenskan, Elitettan) leaked through for 2 weeks; one 72%-confidence miss polluted the owner's sacred 70%+ bucket, and the owner caught it **by luck** comparing the dashboard across two days. Nothing automated would ever have flagged it. Permanent three-layer fix, never remove any of them: (1) **pattern backstop** `is_womens_match()` in all four scripts — both team names ending in " W"/"(W)" (API-Football's women's convention) exclude the match regardless of league name; (2) **post-grading sentinel** `post_grading_alerts()` in `predict_v2.py` runs every morning after resolution: any NEW 70%+ miss is Telegram'd to the owner with full details, and `find_data_leaks()` scans BOTH engines' memories (all pending + last-2-days resolved) for banned patterns and shouts if anything got in; (3) **regression tests** for both layers in `tests/test_exclusions.py`. Standing rule from this incident: **every blocklist-style filter must ship with a pattern-based backstop and a sentinel that audits what actually entered the data — silence is not evidence of cleanliness.** The rule proved itself the very next day (2026-08-02): "Costa Rica U21" leaked into the live list through a league name carrying no youth keyword — patched with the second pattern backstop `is_youth_match()` (both team names carrying U16–U23) in all four scripts at the same gate as `is_womens_match()`, covered by `find_data_leaks()` and `tests/test_exclusions.py`.
- **The unstaged-file push failure (2026-08-09) — a hand-written `git add` list is a time bomb.** Two consecutive monitor runs (21:00 and 21:10 UTC) failed outright at the Save-state step and `data.json` on main froze. The runs did all their real work and even committed locally ("7 files changed"), but the push never happened: the step stages a **hand-maintained list** of filenames, then runs `git pull --rebase` before pushing. Any tracked file the run touches that is not in that list stays modified in the working tree, and git refuses to rebase a dirty tree — `error: cannot pull with rebase: You have unstaged changes.` All five retries hit the same wall, the step exited 1, and the runner was destroyed with the data still on it. **This class of failure never heals itself**: every later run repeats it, so one new file silently ends all data writes — the same end state as the 2026-08-06 jam, reached by a different road. Permanent fix: `git add -A` in the Save step of **all three** data-writing workflows (`monitor.yml`, `predict.yml`, `predict_v2.yml` — the two predict workflows carried the identical latent fault, e.g. predict.yml never staged `state.json`, `history.json`, `lessons_v2.json`, `radar_log.json`). Safe because `.gitignore` already excludes `__pycache__/`. Guarded by `tests/test_workflow_commit_all.py`, which fails on any return of a named-file `git add` before a rebase and also asserts the retry loop and its explicit `[ "$ok" = "1" ]` failure are still in place. **Standing rule from this incident: never enumerate files before a rebase-and-push — stage everything the run produced, or the next file added to the project silently stops all writes.**
- **The run-overrun jam (2026-08-06) — a run that outlasts its slot destroys its own data.** On a busy evening the monitor produced **no successful run for 7 hours 23 minutes** (15:40 → 23:10 UTC) and `data.json` on main stayed frozen at 15:59 — the dashboard's staleness badge was the only visible symptom. Root cause, proven from job timestamps (three consecutive jobs each ran exactly 15:01/15:01/15:02 and each died at the exact second its successor started): the fast-watch deadline was computed **after** the normal pass, so a run's length was "however long the pass took, plus 8 minutes" — unbounded. On a heavy evening the pass alone takes 6–7 min (up to 12 Engine-2 live analyses on Fable-5 with extended thinking, plus pulses), runs overshot the 10-minute ping interval, a queue formed, and every arriving run evicted the one still working **before it reached the Save-state step**. `cancel-in-progress: false` does not protect against this — it was already set. Two diagnoses were published to the owner before the right one; both are recorded here because the wrong ones cost hours: it is NOT a concurrency-config bug and NOT a fast-watch budget bug. Permanent fix: `fast_watch_deadline()` anchors the deadline to `RUN_START` and caps monitor.py at `RUN_WALL_CLOCK_BUDGET_SECONDS=7*60`, leaving ~3 min for dashboard_update + watchdog + save; `FOCUS_LOOP_BUDGET_SECONDS` dropped 8→6 min because an 8-minute budget could never fit inside the cap and was a promise that never held. Alert latency is unchanged — it is set by `FOCUS_SWEEP_SECONDS=90`, not by loop length (four sweeps instead of five). Guarded by `tests/test_run_budget.py`, whose core assertion is that no elapsed pass duration can push the deadline past the slot. **Standing rule from this incident: any loop that keeps a scheduled run alive must be bounded from the run's start, never from the moment the loop begins — otherwise the schedule silently becomes a queue and the queue eats the writes.**
- **The stale-screen lesson (2026-08-02) — a fix that reaches the repo but not the open screen is not a fix.** The frozen-minute repair merged while the owner's TV tab still ran the old page code and pre-fix data, so he saw the same bug minutes later. Three permanent layers now close this class: (1) **self-updating page** — `IM_BUILD` constant in index.html + `checkSelfUpdate()` polls every 10 min and auto-reloads when a newer build is published; **standing rule: bump `IM_BUILD` in every PR that touches index.html**; (2) **visible staleness badge** — if `data.json` is >20 min old while live matches exist, the header timestamp turns amber with "البيانات متأخرة عن الواقع" (client-side, independent of backend); (3) **freshness sentinel** — `freshness_warnings()` in dashboard_update.py prints loudly in the Actions log when live snapshots are missing `seen` stamps or older than 20 min. The heartbeat guard should also glance at data.json age when checking monitor cadence.
- `scan.yml` was once nested at `.github/workflows/.github/workflows/` — invisible to Actions. Fixed. Watch for path mistakes.
- Secrets once contained: (a) a trailing newline that broke HTTP headers, (b) the football key pasted into the Anthropic secret. Both diagnosed via a temporary debug workflow. Scripts now strip whitespace.
- A debug script once leaked a key into a committed file via an exception message; history was force-push scrubbed and the key rotated. Hence rule 3 above.
- API keys were exposed in a screenshot early on and rotated. Assume any key that ever appeared in plain text is dead.
- Local standalone HTML was tried and abandoned: iOS Files preview doesn't execute JavaScript. GitHub Pages is the chosen architecture.
- `monitor.yml`, `predict.yml`, and `predict_v2.yml` share concurrency group `football-monitor` and use `git pull --rebase` before push to avoid commit races; all commit with `[skip ci]`. `scan.yml` commits nothing so it has no concurrency group.
- **GitHub's cron is best-effort, not guaranteed**: on 2026-07-14 GitHub silently skipped both daily prediction runs (03:15/03:30 UTC) and left an 8.5h gap in the 20-min monitor cron. Permanent mitigation (four layers, keep all of them): (1) the scheduler watchdog in every monitor run, (2) backup cron slots one hour after the primary with a same-day guard, (3) duplicate runs are harmless by design — resolve is idempotent, already-pending fixtures are skipped, and no digest is sent when there is nothing new, (4) **external cron pinger — LIVE since 2026-07-14**: a cron-job.org job ("InsightMatch monitor", on the owner's account) POSTs to the workflow-dispatch API for monitor.yml every 10 minutes with a fine-grained PAT named `insightmatch-pinger` (this repo only, Actions: read/write, no expiration). The monitor's in-repo watchdog then guarantees the daily prediction runs, so this one ping keeps the whole system alive regardless of GitHub's scheduler. Note: the pinned API version header `2022-11-28` has a published sunset of 2028-03-10 — bump the `X-GitHub-Api-Version` header in the cron-job.org job before then, (5) **backup heartbeat**: three permanent Claude Routines (staggered :05/:25/:45 hourly, named "InsightMatch pinger A/B/C") in the owner's Claude session infrastructure re-trigger monitor.yml if the newest run is older than 15 min and fire missed daily prediction runs in V1-then-V2 order — normally dormant while the cron-job.org pinger works.

## Data exploration doctrine (owner's directive 2026-07-15 — never stop, but go gradually)

The set of signals Engine 2 consumes must **keep expanding forever** — exploring new data is itself part of the self-learning. Rules:

1. **One new source per PR** — never bundle two experiments, so any single addition can be rolled back with one revert if the accuracy trend drops.
2. **Measure before judging — on SAMPLE SIZE, never calendar days (owner's correction 2026-08-01: "7 days is never enough")**: after adding a source, watch the `history.json` daily trend (and the V1-vs-V2 gap) for **at least 3 weeks or one full round of the priority leagues, AND until a pre-registered minimum sample is reached (≥100 graded matches for engine-level signals; ≥150 graded bullets for report-level claims) — whichever comes later**. A 7-day read can be a lucky streak that fakes genius or a bad week that kills a good idea. Improvement on sufficient sample → keep; degradation → revert that PR.
3. **Small signals matter**: the owner explicitly wants beyond-the-headlines data — a coach's identity ("if the coach is Maradona, that makes a difference"), cup vs league context, player transfers, niche news, even geopolitics where relevant.
4. **Status so far** — integrated: standings, h2h last 5, form last 5, injuries, bookmaker odds (implied probabilities), API-Football statistical prediction, RSS headlines (now incl. Sky News for transfer/small news), calibration record, lessons notebook, **coach identity (`coachs` endpoint, both teams)**, **competition context (round/stage/leg from fixture data — free)**, **travel & environment (venue+city from fixture data; the model estimates the away side's flight distance, time zones, climate/altitude — free)**, **rest days since each team's last match (computed from the form fetch — free)**, **recent transfers last 90 days (`transfers` endpoint, 2 calls/fixture)**, **kickoff weather (Open-Meteo geocoding+forecast — free, no key; `_GEO_CACHE` per run; silent-fail)**, **targeted per-team news for pre-match reports (Google News RSS, free — `team_news_headlines()` in monitor.py) AND for every priority-league daily prediction (owner's request 2026-07-18: widen the same legit feed to every top fixture to lift the "protection rate" — `team_news_context()` in `predict_v2.py`, wired into `build_context`, free, silent-fail, Engine-2-only; NOTE: the 433 social-media community was evaluated and rejected as an entertainment/low-signal source with no legitimate feed — conflicts with the clean-data rule)**, **self-built referee DB (`referees.json`: fed by `record_referee()` from every scenario-graded match's stats; consumed by the pre-match report — announced referee + card averages)**. Steps 3–6 landed together on the owner's explicit instruction 2026-07-15 ("start from zero to three"); each is an isolated function + one build_context line, so any single one can still be reverted surgically if the trend dips.
5. **Next candidates (in rough order)**: Sportmonks xG (ACTIVE — see rule 8); **final-call update layer (owner's gap-finding 2026-07-31, queued directly after xG)**: the morning prediction is frozen by design (pre-registration integrity + V1/V2 fairness — NEVER let it be overwritten), but late-breaking info (lineups, late injuries, odds moves) currently influences nothing except the T-45 report for watchlist/shadow matches. Design: a near-kickoff refresh records a SECOND number `pred_final` with a stated reason next to the untouched frozen `confidence`, shadow-graded separately for 2–3 weeks before earning any official status. Pre-registered expectation: decisive late news in ~5–10% of matches, ~+3–5 pts on that subset (mostly lineups), near zero on the rest.
