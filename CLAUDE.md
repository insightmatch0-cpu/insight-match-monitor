# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the complete context for the InsightMatch football monitoring & prediction system. Any AI agent working in this repo must read this first and follow it exactly.

## Who the user is

Nayef — the owner and sole operator. **No coding experience.** Always explain in plain language, provide step-by-step instructions for anything manual, and never assume he can debug code himself. He works mostly from an iPhone, sometimes a Mac. Communication may be voice-transcribed (tolerate imprecise wording; confirm intent when ambiguous).

## What this system is

A fully automated football match monitoring, alerting, and self-learning prediction system running entirely on free/low-cost infrastructure:

- **GitHub Actions** (public repo = unlimited minutes) — all automation. Python 3.12, sole dependency: `requests` (installed per-run in workflows; there is no requirements.txt)
- **API-Football** (api-sports.io, **Pro plan: 7,500 requests/day**) — match data. Key in GitHub Secret `API_FOOTBALL_KEY`
- **Anthropic Claude API** (model `claude-haiku-4-5-20251001`, set as `CLAUDE_MODEL` in each script) — all analysis & predictions. Key in Secret `ANTHROPIC_API_KEY`
- **Telegram bot** — alert delivery. `TELEGRAM_TOKEN` + `TELEGRAM_CHAT_ID` in Secrets
- **GitHub Pages dashboard** — https://insightmatch0-cpu.github.io/insight-match-monitor/

## The self-learning loop (core logic — preserve it)

1. Every prediction is stored with pick (`home|draw|away`) + confidence (prompt asks for 40–80; parser clamps to 30–85).
2. Next morning, `predict.py` fetches real results and grades each prediction — **on the 90-minute score** (`score.fulltime`, falling back to `goals`): a knockout match decided in extra time/penalties still grades as a draw if level after 90, matching the universal 1X2 convention (and the odds fed to V2).
3. Accuracy is computed: overall, last 30 days, top vs other leagues, daily series (last 30 days), and **by confidence bucket** (70+, 60-69, 50-59, <50).
4. That track record is injected into every new Claude prediction prompt with the instruction: *if your real accuracy is below your stated confidence, lower your confidence — and vice versa.* This calibration IS the learning mechanism. Never remove it.

## Engine 2 (V2)

The second-generation prediction engine (`predict_v2.py`), built to run side-by-side with Engine 1 for a fair, direct comparison. Design decisions — preserve them:

- **Same fixtures as V1**: identical next-24h selection, exclusion lists, `TOP_LEAGUE_IDS`, and `MAX_PREDICTIONS_24H=150` (raised from 60 on 2026-07-18 so later-kickoff evening matches are also predicted — otherwise they showed live on the dashboard with no engine 'protection' chip; must stay identical in both engines, guarded by `tests/test_exclusions.py`), so accuracy numbers are comparable engine-to-engine.
- **Model**: `claude-fable-5` (V1 stays on Haiku).
- **Enriched context, top leagues only by default** (`ENRICH_TOP_ONLY=True`, cost control 2026-07-17): the heavy enriched prompt (and Fable's cost on it) is spent on top-league fixtures; every other fixture is still predicted and graded, just with the lean prompt — so coverage, grading, calibration, and lessons are unchanged, only the token bill drops. Set `ENRICH_TOP_ONLY=False` to instantly restore rich context for every fixture. When a fixture is enriched, extra API-Football data is fetched before predicting — standings of both teams (1 call per league, cached per run), head-to-head last 5, each team's last 5 results, injuries, **bookmaker odds** (first bookmaker's Match Winner odds, converted to implied probabilities with the overround removed — the prompt instructs Claude to treat the market as a strong reference but diverge with a stated reason), and **API-Football's own statistical prediction** (percentages + advice). `MAX_ENRICHED_FIXTURES=60` caps how many fixtures may be enriched, and `ENRICH_CALL_BUDGET=750` caps the extra calls/run as a safety net; enrichment failures degrade gracefully to a basic prediction (never kill the run).
- **Probability output**: each prediction returns `prob_home`/`prob_draw`/`prob_away` as integers summing to 100 (parser normalizes if they don't). `pick` = highest probability; `confidence` = that probability clamped 30–85. Probabilities are stored in pending AND resolved entries.
- **Cup/knockout guardrail (`CUP_GUARDRAIL`, owner's priority 2026-07-18)**: the owner watches the **70%+ confidence bucket** closely — it must stay near-perfect. Its single miss was a domestic-cup upset (Kerry 2-2 Shelbourne, FAI Cup, engine gave the away favourite 72%). Fix: `apply_cup_guardrail()` runs after the model on cup/knockout fixtures (`is_cup_fixture()` flags them by league-name/round keywords — cups + UEFA qualifiers) and (a) raises the draw probability to a floor `CUP_MIN_DRAW=25` — cup upsets are common, and (b) caps confidence at `CUP_CONF_CAP=65` so cup guesses can never enter the 70%+ high-conviction tier. It **never changes which side is picked** (the draw floor never exceeds the favourite) and **does not touch learning** — calibration + lessons still grade against the real result. The engine's own lessons loop already learned this pattern ("beware >70% confidence in cup matches"); this converts that soft lesson into a hard guardrail for the high-stakes tier. Instant revert: `CUP_GUARDRAIL=False`.
- **Batching**: enriched fixtures in batches of `ENRICHED_BATCH_SIZE=4` (context is bulky), basic fixtures in batches of `BASIC_BATCH_SIZE=12` like V1. Strict JSON output, tolerant parser — same rule 6.
- **Own memory**: `predictions_v2.json` (`pending`/`resolved`/`meta.stats`), fully separate from V1, with the exact same grading, resolution, and calibration-stats logic — the calibration record is injected into every V2 prompt just like V1.
- **Lessons loop (Phase 3 — LIVE)**: every morning, after grading, `generate_lessons()` sends up to `MAX_MISTAKES_PER_RUN=30` (i.e. effectively ALL) of yesterday's WRONG predictions to Claude in one call, which extracts one short, generalizable Arabic lesson per mistake (a pattern to watch for, not a description of the game). Lessons are stored in `lessons_v2.json` as `{"date","match","text"}` (capped at `MAX_LESSONS_STORED=100`); the most recent `MAX_LESSONS_IN_PROMPT=15` are injected into every prediction prompt under "دروس من أخطائك السابقة". **Consolidation**: when stored lessons exceed `CONSOLIDATE_THRESHOLD=60`, one Claude call merges similar lessons into ≤`CONSOLIDATE_TARGET=30` stronger general principles (entries labeled "خلاصة مُجمّعة"); on any parse failure the original lessons are kept untouched. The newest 10 lessons also appear on the dashboard (V2 tab) and the digest notes how many new lessons were learned. Note: calibration (the accuracy record in every prompt) already learns from ALL graded matches — the lessons loop is the qualitative layer on top.
- **Telegram digest** is labeled "🤖 المحرك 2" so V1 and V2 messages are distinguishable; it shows the three probabilities per match AND, for each match, Engine 1's pick next to Engine 2's pick (read from `predictions.json` pending — V2 runs 15 min after V1 so V1's picks already exist). The side-by-side comparison lives in the V2 digest only; V1's digest is unchanged.
- **Live layer (in `monitor.py`)**: top-league live matches are analyzed by `claude-fable-5` with **extended thinking** (`LIVE_THINKING_BUDGET=2048` tokens of deep reasoning before answering) fed with real live statistics + events + **lineups/formations** (3 API calls per match) and an all-scenarios prompt. Capped at 12 matches per run. **Scenario menu (`SCENARIO_MENU_V2`, owner's market-style list 2026-07-15, shared by the event analysis AND the pulse)**: next goal + likely scorer/assister by name, both-teams-to-score, total-goals trajectory (open/closed game), corner waves + which team wins most, set pieces (dangerous free kicks, long throw-ins near the box, repeated goal kicks/clearances as pressure signals), cards (named player likely to be booked, game-changing red, both teams carded), goalkeeper under siege (repeated saves), repeated offsides killing attacks, and endgame shape (winning margin, which half has more goals, HT/FT swing, leader closing the game). The live stats fed in include shots on/off/blocked/inside/outside box, offsides, saves, fouls (`KEY_LIVE_STATS`).
- **Logo self-repair**: both engines backfill missing `home_logo`/`away_logo`/`league_logo` on pending entries from the daily fixtures fetch, and fill them from the results fetch at resolve time — zero extra API calls.
- **Budget**: 2 fixture-date calls + ≤3 resolve calls + enrichment (typically ~385 incl. odds + model predictions, hard-capped at 600) ≈ ~400/day on top of V1's 5.

## Analysis methodology (the user's expert framework — apply in all analysis)

**Pre-match factors:** league position; motivation (title race / qualification / relegation); first or second leg + first-leg result; home/away records; current streaks; head-to-head; key injuries & suspensions; goals scored/conceded (attack vs defense); form trajectory last 5–6 games; manager situation (new appointment bounce / under pressure); fixture congestion & rotation risk before bigger matches; derby/clásico factor (these defy logic).

**Live-match additions:** xG; shots on/off target; possession *tied to real danger* (possession alone deceives); key passes; dangerous attacks (note surges in final 10–15 min); corners; red cards (who, when, position); current minute; score-line behavior (is the leader defending or pushing); substitutions (extra striker vs closing the game).

**Output format for any prediction:** short focused analysis of relevant factors only → clear final verdict: winner or draw + confidence % → for live matches, likely next scenario. Occasionally remind (briefly, not every reply): predictions are analytical opinions, never guarantees.

## Project history & lessons learned

- **The dedup race, episode 2 — same day (Cracovia د45 ×2): checking the durable store is not enough if nothing writes to it at send time.** Hours after the Drukpa fix merged, the owner received the SAME early red warning twice again (Cracovia 1-1 Wieczysta, د45 at 10:24 PM and 10:31 PM). The #143 gate read `radar_log.json` correctly — but found nothing, because **the fast lane never wrote a warning row at all**, and the sweep's row (with `alerted`) reached disk only at sweep end, which an evicted run never reaches. The gate was honest; the store was empty. Completion of the fix: `_upsert_warn_row()` + `_flush_radar_log()` — the alert function itself upserts the `alerted` row into the log and, in the fast lane, **writes the file in the same breath as the Telegram send**; in the sweep, the shared live log is flushed immediately after any iteration that sent an alert (drama, red-advantage, or early warning), while the end-of-sweep save remains as the normal path. Side benefit: fast-lane sends are now measurable rows (they previously vanished from the sent-slice scoreboard). Regression tests in `tests/test_radar.py` (`TestDurableWriteAtSendTime`: fast-lane send lands on disk immediately; an evicted first run cannot cause a repeat; structural pin on the sweep flush). **The standing rule below is thereby sharpened: it is not enough that the dedup gate READS a durable store — the send path must WRITE that store at the moment of sending, in every lane that can send.**
- **The two-store dedup race (2026-08-21) — a flag that outlives the run only if the run finishes.** The owner received the SAME early red warning twice (Drukpa 2-2 Thimphu City, «د84» 4:41 PM then «د85» 4:43 PM), although `maybe_red_warning_alert()` is once-per-match by design and `radar_log.json` held exactly ONE row for that fixture. Root cause: the dedup flag `warn_alerted` lives in `state.json`, which is written by `save_state()` at the **end** of the run, while the alert's own record lands in `radar_log.json` **during** the sweep. A run evicted between the two (the every-10-min slot, exactly the 2026-08-06 jam pattern) therefore **delivers the Telegram and loses its flag** — the next run sees a clean slate and re-alerts, while the log keeps one row so nothing looks wrong afterwards. Fix: a second, durable gate — the alert now also checks the sweep's live `radar_log` for an existing `alerted` row on that fixture and, when it finds one, rebuilds the missing in-memory flag before returning silently. The log is the store that is written at send time, so it is the only honest dedup source. Regression tests in `tests/test_radar.py` (repeat blocked across runs, first alert still allowed, structural pin that the sweep passes its live log). **Standing rule from this incident: a dedup flag for a user-visible side effect must live in a store that is persisted at the moment the side effect happens — a flag saved at end-of-run protects nothing against a run that never reaches its end.**
- **The sweep-clobber race (2026-08-15) — two writers to one file, and the slower one always wins.** Two drama alerts (Mito Hollyhock next_goal 10:42 UTC, Alverca red_advantage 16:10 UTC) reached the owner's Telegram and then vanished from `radar_log.json` entirely — never graded, silently missing from the drama scoreboard. Commit-history trace proved they were **never on disk in any commit**: `radar_sweep()` loads its own copy of the log at sweep start and saves it at sweep end, while `maybe_radar_alert()`/`maybe_red_alert()` (called inside the sweep loop) each did their own load→append→write — so the sweep's final save, made from its pre-alert copy, clobbered every alert fired during that sweep. Alerts fired from the fast lane (after the sweep's save) survived, which made the loss look random. Fix (PR #104): single-writer discipline — the sweep passes its live `log` object into both alert paths (`log` parameter; fast-lane calls without it keep the old direct write), and an alert marks `log_dirty` so the shared object is always persisted. The two destroyed alerts were reconstructed from Telegram evidence + engine data and restored with a `restored: true` marker (empty evidence pack — the original snapshots are unrecoverable). Regression tests in `tests/test_radar.py` (race re-enactment + structural pin on the shared-log call). **Standing rule from this incident: within one process, one file gets one writer — any helper that must write mid-cycle takes the cycle's live object, never re-reads the file; and any "sent to the user" artifact must be verifiable in the measurement log the same day it fires.**
- **The reserved-keys erasure (2026-08-15) — the guard's memory lived inside the map the cleaner sweeps.** The delivery-receipts layer (PR #98) worked perfectly — and looked completely dead: `state.json → delivery` was always null. Found during the owner-ordered full assurance audit by tracing the key through state.json's commit history: every broadcast DID record the pulse («2/2» at 15:35 and 16:10, matching two radar alerts to the minute), and **the very next monitor cycle erased it** — the end-of-run memory cleanup deleted every top-level key not in `live_ids`, i.e. every reserved guard key. Blast radius beyond `delivery`: `api_alerts` (the 6h throttle flags — their erasure re-arms the exact message flood the throttle was built to stop) and `deadman.alerted_for` (its erasure would have made the external dead-man alert fire every 10 minutes instead of once per day, on the very day it is needed). Same class as WK-League: a delete-everything-not-recognized loop is a blocklist that FAILS OPEN — any future reserved key would be silently swept too. Fix (PR #100): `prune_dead_matches()` deletes **numeric keys only** (fixture ids are always `str(fixture.id)`), so any reserved key — present or future — survives with no list to maintain (fails CLOSED); regression tests in `tests/test_state_reserved_keys.py` (behavioral + a structural test that fails if the bare delete loop ever returns). **Standing rule from this incident: any cleanup/prune loop must select what it deletes by a positive pattern of the data it owns, never by "everything I don't recognize" — and any new key added to a shared store must be tested against every loop that sweeps that store.**
- **The silent-failure blackout (2026-08-14) — a watchman that lives inside the thing it watches is not a watchman.** The API-Football subscription lapsed and the account fell back to the free plan (100 calls/day instead of 7,500). A normal match day needs ~2,366 calls, so the balance was gone within an hour: zero predictions, zero reports, zero radar alerts, two important matches lost. The morning run failed twice and then went quiet, and **the owner did not find out for 19 hours — he discovered it himself, from his phone.** The lapse itself is ordinary; the 19 hours of silence are the incident. Three independent root causes each had to hold for the system to stay this quiet, and all three are now fixed in `api_guard.py` / `deadman.py`: **(1) rule 5 was overloaded** — `monitor.py` treated a provider refusal exactly like "a quiet day with no matches" and swallowed it, so the dashboard reported calm skies while the account was dead; "no data" and "refused" now travel separate code paths and rule 5 says so explicitly. **(2) The alert threshold outran the failure** — the guard notified only after *three* consecutive failed runs, and exactly two occurred, so the threshold was never crossed; alerting is now immediate on the **first** refusal, with a 6h-per-fault-type throttle in `state.json` doing the anti-flood work that a naive counter was pretending to do. **(3) The integrity sentinel ran inside `predict_v2.py`** — when the engine died, its watchman died with it; the replacement (`deadman.py`) runs in `monitor.yml`, every 10 minutes, with zero API calls and no dependency on either engine, and says «⚠️ لم يجرِ التقييم الصباحي اليوم» once a day if `history.json` hasn't advanced. A fourth, quieter fix removes the whole class of surprise: the balance is now **visible** — every response's rate-limit headers are stored and the morning digest carries "📊 رصيد API: مستهلك X من Y", with a proactive warning under 20% remaining. Had that line existed, the ceiling reading 100 instead of 7,500 would have been on the owner's phone that morning. **Three standing rules from this incident: (a) a threshold that needs N failures will be defeated by N−1 — alert on the first one and throttle the repeats instead; (b) never let a guard depend on the health of what it guards; (c) make the resource you depend on visible every single day, because the failure you can see coming is not the one that kills you.** Guarded by `tests/test_silent_failure_guard.py`.
- **The WK-League incident (2026-08-01) — the data-quality doctrine.** The clean-data filter was a keyword blocklist, and blocklists FAIL OPEN: 4 women's leagues whose names carry no keyword (WK-League, Kvindeliga, Damallsvenskan, Elitettan) leaked through for 2 weeks; one 72%-confidence miss polluted the owner's sacred 70%+ bucket, and the owner caught it **by luck** comparing the dashboard across two days. Nothing automated would ever have flagged it. Permanent three-layer fix, never remove any of them: (1) **pattern backstop** `is_womens_match()` in all four scripts — both team names ending in " W"/"(W)" (API-Football's women's convention) exclude the match regardless of league name; (2) **post-grading sentinel** `post_grading_alerts()` in `predict_v2.py` runs every morning after resolution: any NEW 70%+ miss is Telegram'd to the owner with full details, and `find_data_leaks()` scans BOTH engines' memories (all pending + last-2-days resolved) for banned patterns and shouts if anything got in; (3) **regression tests** for both layers in `tests/test_exclusions.py`. Standing rule from this incident: **every blocklist-style filter must ship with a pattern-based backstop and a sentinel that audits what actually entered the data — silence is not evidence of cleanliness.** The rule proved itself the very next day (2026-08-02): "Costa Rica U21" leaked into the live list through a league name carrying no youth keyword — patched with the second pattern backstop `is_youth_match()` (both team names carrying U16–U23) in all four scripts at the same gate as `is_womens_match()`, covered by `find_data_leaks()` and `tests/test_exclusions.py`.
- **The unstaged-file push failure (2026-08-09) — a hand-written `git add` list is a time bomb.** Two consecutive monitor runs (21:00 and 21:10 UTC) failed outright at the Save-state step and `data.json` on main froze. The runs did all their real work and even committed locally ("7 files changed"), but the push never happened: the step stages a **hand-maintained list** of filenames, then runs `git pull --rebase` before pushing. Any tracked file the run touches that is not in that list stays modified in the working tree, and git refuses to rebase a dirty tree — `error: cannot pull with rebase: You have unstaged changes.` All five retries hit the same wall, the step exited 1, and the runner was destroyed with the data still on it. **This class of failure never heals itself**: every later run repeats it, so one new file silently ends all data writes — the same end state as the 2026-08-06 jam, reached by a different road. Permanent fix: `git add -A` in the Save step of **all three** data-writing workflows (`monitor.yml`, `predict.yml`, `predict_v2.yml` — the two predict workflows carried the identical latent fault, e.g. predict.yml never staged `state.json`, `history.json`, `lessons_v2.json`, `radar_log.json`). Safe because `.gitignore` already excludes `__pycache__/`. Guarded by `tests/test_workflow_commit_all.py`, which fails on any return of a named-file `git add` before a rebase and also asserts the retry loop and its explicit `[ "$ok" = "1" ]` failure are still in place. **Standing rule from this incident: never enumerate files before a rebase-and-push — stage everything the run produced, or the next file added to the project silently stops all writes.**
- **The run-overrun jam (2026-08-06) — a run that outlasts its slot destroys its own data.** On a busy evening the monitor produced **no successful run for 7 hours 23 minutes** (15:40 → 23:10 UTC) and `data.json` on main stayed frozen at 15:59 — the dashboard's staleness badge was the only visible symptom. Root cause, proven from job timestamps (three consecutive jobs each ran exactly 15:01/15:01/15:02 and each died at the exact second its successor started): the fast-watch deadline was computed **after** the normal pass, so a run's length was "however long the pass took, plus 8 minutes" — unbounded. On a heavy evening the pass alone takes 6–7 min (up to 12 Engine-2 live analyses on Fable-5 with extended thinking, plus pulses), runs overshot the 10-minute ping interval, a queue formed, and every arriving run evicted the one still working **before it reached the Save-state step**. `cancel-in-progress: false` does not protect against this — it was already set. Two diagnoses were published to the owner before the right one; both are recorded here because the wrong ones cost hours: it is NOT a concurrency-config bug and NOT a fast-watch budget bug. Permanent fix: `fast_watch_deadline()` anchors the deadline to `RUN_START` and caps monitor.py at `RUN_WALL_CLOCK_BUDGET_SECONDS=7*60`, leaving ~3 min for dashboard_update + watchdog + save; `FOCUS_LOOP_BUDGET_SECONDS` dropped 8→6 min because an 8-minute budget could never fit inside the cap and was a promise that never held. Alert latency is unchanged — it is set by `FOCUS_SWEEP_SECONDS=90`, not by loop length (four sweeps instead of five). Guarded by `tests/test_run_budget.py`, whose core assertion is that no elapsed pass duration can push the deadline past the slot. **Standing rule from this incident: any loop that keeps a scheduled run alive must be bounded from the run's start, never from the moment the loop begins — otherwise the schedule silently becomes a queue and the queue eats the writes.**

Three permanent layers now close this class: (1) **self-updating page** — `IM_BUILD` constant in index.html + `checkSelfUpdate()` polls every 10 min and auto-reloads when a newer build is published; **standing rule: bump `IM_BUILD` in every PR that touches index.html**; (2) **visible staleness badge** — if `data.json` is >20 min old while live matches exist, the header timestamp turns amber with "البيانات متأخرة عن الواقع" (client-side, independent of backend); (3) **freshness sentinel** — `freshness_warnings()` in dashboard_update.py prints loudly in the Actions log when live snapshots are missing `seen` stamps or older than 20 min. The heartbeat guard should also glance at data.json age when checking monitor cadence.

## Data exploration doctrine (owner's directive 2026-07-15 — never stop, but go gradually)

The set of signals Engine 2 consumes must **keep expanding forever** — exploring new data is itself part of the self-learning. Rules:

1. **One new source per PR** — never bundle two experiments, so any single addition can be rolled back with one revert if the accuracy trend drops.
2. **Measure before judging — on SAMPLE SIZE, never calendar days (owner's correction 2026-08-01: "7 days is never enough")**: after adding a source, watch the `history.json` daily trend (and the V1-vs-V2 gap) for **at least 3 weeks or one full round of the priority leagues, AND until a pre-registered minimum sample is reached (≥100 graded matches for engine-level signals; ≥150 graded bullets for report-level claims) — whichever comes later**. A 7-day read can be a lucky streak that fakes genius or a bad week that kills a good idea. Improvement on sufficient sample → keep; degradation → revert that PR.
